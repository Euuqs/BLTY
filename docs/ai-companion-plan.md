# 柏里挑怡 AI 故事陪伴者实施计划

> 版本：v1.0 · 2026-09-07  
> 来源：基于共享聊天整理，并结合当前 `cp-site` 仓库结构校准。  
> 目标：在现有 Next.js 网站中增加一个独立的 AI 故事陪伴者，让用户既能自然聊天，也能基于真实资料回忆故事，并被带回站内相关内容。

## 一、产品定义

陪伴者是网站中的独立角色，不冒充柏欣妤或朱怡欣本人。它应当：

- 能处理普通陪聊，不因每句话都触发资料检索。
- 能回答与时间、活动、动态和故事有关的问题，并优先依据站内资料。
- 能区分事实、站长整理的理解和未知信息，不为了陪伴感而编造。
- 能结合用户当前正在浏览的页面理解“这个”“那次”等指代。
- 在合适时主动推荐 0～2 个站内故事或内容卡片，推荐项只能引用真实内容 ID。
- 默认保持自然聊天；只有用户追问出处时才展开来源。

首版的成功标准不是“用了最先进的 RAG”，而是用户能感到：它知道正在聊谁、记得真实发生过什么、不会乱编，并能自然地把聊天带回值得重看的站内内容。

## 二、当前仓库基线

当前项目已具备继续扩展所需的基础，不需要重构技术栈：

- Next.js 16、React 19、TypeScript、Tailwind CSS 4、Motion、Velite + MDX。
- 现有公开内容包括 `same-styles`、`schedules`、`feeds` 三个集合。
- 前台统一通过 `src/lib/velite.ts` 读取已发布内容。
- 已有搜索 API、详情弹窗、全局导航、主题/声音/反馈 Provider，可复用现有交互和视觉基础。
- 独立本地内容编辑器已经完成三类内容的安全写回、草稿、发布和 Git 流程，后续应在该编辑器中追加故事库管理，而不是在前台网站再做一个后台。

## 三、首版范围

### 必须完成

1. Companion 人格与事实边界。
2. 独立 `stories` 内容集合和首批 30～50 条高质量故事。
3. 普通陪聊 / 故事查询的意图路由。
4. 基于关键词、时间、人物和标签的轻量检索。
5. 可替换的模型 Provider 层，首版只接通一个真实模型。
6. `/api/companion/chat` 服务端接口和流式回复。
7. 全局聊天抽屉，兼容桌面和移动端。
8. 当前页面上下文和站内内容推荐卡片。
9. 匿名用户的本地轻量记忆。
10. 公开上线前的限流、预算保护、错误降级和隐私说明。
11. 50～100 条固定评测集，覆盖陪伴、故事、来源和防幻觉。

### 首版明确不做

- 不训练模型，不 Fine-tuning。
- 不做复杂 Agent、多 Agent或声音克隆。
- 不上向量数据库、Reranker 或完整 RAG 框架。
- 不自动爬取外部明星资料。
- 不做账号系统、跨设备长期记忆或无限聊天历史。
- 不让模型直接生成站内 URL，也不允许未经验证的内容 ID 出现在推荐中。
- 不同时完成四家模型的生产接入；多模型竞技场属于验证阶段能力。

## 四、数据设计

新增 Velite 集合：

```text
content/companion/
├── personality.md
└── stories/
    └── <story-id>.mdx
```

建议的故事 frontmatter：

```yaml
id: story-2023-0520-001
slug: 2023-05-20-example
status: published
title: 某次活动
date: 2023-05-20
member: both
era: 2023夏季
arc: 某段故事线
types:
  - event
  - interaction
tags:
  - 上海
  - 活动
moods:
  - 开心
  - 温柔
summary: 用一两句话说明发生了什么。
facts:
  - 已确认事实一
  - 已确认事实二
interpretation: 站长对事件意义的理解；不能作为事实引用。
meaning: 为什么值得记住，以及与前后故事的联系。
related:
  - type: feed
    id: stable-content-id
sources:
  - title: 来源标题
    url: https://example.com/source
confidence: confirmed
```

MDX 正文用于完整叙事。`facts`、`interpretation` 和正文必须分开；模型提示词明确规定，事实回答只能依据 `facts`、已确认正文和来源，解释性内容必须使用不确定语气。

关联内容使用 `{ type, id }`，不保存模型生成的 URL。前台收到 ID 后再从 Velite 集合解析实际标题、摘要和链接。

## 六、分阶段实施

### Phase 0 · 契约与安全边界

- 固定陪伴者人格、禁止行为、事实/推测/未知的表达规则。
- 定义聊天请求、流式事件、错误事件和推荐卡片契约。
- 定义最大输入长度、最近对话轮数、单次输出上限和超时。
- 规定不默认记录原始聊天内容；日志只保留请求 ID、耗时、模型、token、检索数量和错误类型。
- 模型版本、价格、地域可用性和数据处理条款在接入当天重新核验，不能把共享聊天中的型号与价格写死为项目事实。

验收：类型契约可以独立测试；Prompt 明确不冒充本人、不编造、来源按需展示；密钥不会进入浏览器 bundle 或日志。

### Phase 1 · Story Schema 与内容样本

- 在 `velite.config.ts` 增加 `stories` 集合。
- 在 `src/lib/velite.ts` 增加原始/已发布故事出口。
- 建立 5～10 条覆盖不同年份、情绪、人物和关联类型的开发样本。
- 编写 schema 测试，验证稳定 ID、来源 URL、关联 ID、事实/解释分离和草稿过滤。
- 再通过独立内容编辑器整理首批 30～50 条真实故事。

验收：旧内容构建结果不变；故事草稿不进入生产集合；所有 `related` ID 都能解析或在构建时给出明确错误。

### Phase 2 · 轻量检索与意图路由

- 首版意图路由优先用可解释规则，不额外调用一次模型：识别年份、季节、人物、活动、回忆、来源和事实提问。
- 普通情绪表达、问候、晚安等不检索；故事、时间、事实、出处和“以前发生过什么”等触发检索。
- 对 `title/date/era/arc/member/tags/moods/summary/facts/body` 建立加权评分。
- 支持时间与人物硬过滤，返回 Top 3～5，并设置最低相关度，低于阈值时明确表示资料不足。
- 检索结果附带来源类型和可引用字段，Prompt 不接收无关的全部内容库。

验收：固定查询集能稳定命中目标故事；普通陪聊不搜索；无匹配时不伪造答案。

### Phase 3 · Provider 与聊天 API

- 先实现一个 mock provider，完成无外网、无密钥的接口和 UI 联调。
- 再选择一个真实模型作为开发 provider；其他候选只保留适配接口和评测计划。
- `/api/companion/chat` 使用 Node Runtime，校验请求体、历史轮数、页面上下文和匿名会话 ID。
- 流式协议至少包含 `text-delta`、`recommendations`、`usage`、`error`、`done`。
- 推荐 ID 必须限定在检索候选或当前页面关联项中，并在服务端再次验证；非法 ID 直接丢弃。
- 加入超时、取消、重试边界和无模型时的友好降级。

验收：mock 集成测试通过；真实 provider 能流式回复；断流、超时、配额不足时界面可恢复且不会重复发送。

### Phase 4 · 聊天 UI 与页面联动

- 在根布局挂载 `CompanionProvider` 和全局触发按钮，不新增一级导航页面。
- 桌面端使用右侧抽屉，移动端使用接近全屏的底部面板。
- 支持流式文字、停止生成、重新发送、清空本地历史、加载/错误状态和键盘操作。
- 页面或详情弹窗打开时注册 `{ pageType, contentId, title, date }`；关闭后清理上下文。
- 推荐卡片复用现有内容视觉语言，显示标题、日期、摘要和“去看看”，每次最多 2 张。
- 遵守 44px 触控目标、焦点管理、屏幕阅读器状态提示和 `prefers-reduced-motion`。

验收：桌面与 390px 手机均无横向溢出；用户在动态/行程/同款详情中询问“这个”时上下文正确；推荐能打开真实站内内容。

### Phase 5 · 轻量记忆

- 使用匿名会话 ID + `localStorage` 保存最近 8～12 轮对话、喜欢的故事、常聊时期、看过的推荐和少量显式偏好。
- 服务端只接收本次回答所需的裁剪历史，不把完整历史反复发送给模型。
- 提供“清除聊天与偏好”入口；首版不跨设备同步。
- 不从情绪对话中推断或永久保存敏感画像。

验收：刷新后可恢复最近会话；用户可一键清除；不同浏览器会话相互隔离。

### Phase 6 · 内容编辑器扩展

- 在现有独立编辑器中新增“AI 故事库”：列表、新建、编辑、复制填写、草稿、发布、来源和关联内容选择。
- 表单将事实、解释、意义、正文分区，避免录入时混写。
- 关联内容从现有同款/行程/动态中搜索选择，不手输 URL 或不稳定 slug。
- 增加数据质量提示：缺来源、缺事实、关联失效、时间冲突、重复故事。

验收：故事内容沿用现有安全写回、构建校验、单 commit 和普通 push 流程；不会破坏已有三类内容管理。

### Phase 7 · 评测、成本与公开上线

- 建立 50～100 条版本化测试集，类别包括情绪陪伴、事实查询、时间线、回忆推荐、来源追问、防幻觉和提示注入。
- 盲测候选模型，固定同一 Prompt、同一检索结果和输出长度。
- 建议评分权重：事实准确 30%、不乱编 20%、中文自然 20%、情绪陪伴 15%、故事感 10%、成本与延迟 5%。
- 记录每次评测的 provider、model、Prompt 版本、故事库版本、token、延迟和评分。
- 公开前接入服务端持久限流、每日预算上限、单会话额度、异常告警和紧急关闭开关。
- 小流量灰度，先观察检索命中率、用户停止率、推荐点击率、错误率、P95 延迟和单轮成本。

验收：核心防幻觉用例全部通过；没有来源的问题会承认不知道；预算或 provider 故障时可安全降级；达到质量门槛后才对全部访客开放。

## 七、测试策略

### 自动化测试

- Story schema、草稿过滤、关联 ID 完整性。
- 意图分类和检索排序的固定样例测试。
- Prompt 输入裁剪与事实/解释标记。
- 推荐 ID 白名单验证、URL 解析和页面上下文校验。
- API 请求体、超时、流式事件、错误恢复和 provider mock。
- 本地记忆迁移、过期和清除。

### 人工体验测试

- “今天突然很想她们”“最近没什么新消息”等普通陪伴。
- “2023 年夏天发生过什么”“那件事后来有后续吗”等故事问题。
- “给我找一个以前很开心的故事”等主动回忆。
- “你确定吗”“哪里看到的”等来源追问。
- 故意询问不存在的事件，确认它不会顺着用户编造。
- 在不同详情弹窗中连续询问“这个”，确认上下文不会串页。
- 检查推荐频率，避免每轮都出现卡片而变成广告式体验。

## 八、风险与控制

- **故事质量比模型榜单更重要**：先建立少量高质量、可追溯内容，再扩量。
- **模型信息会快速变化**：provider/model 由配置决定，接入和上线时复核官方文档。
- **提示注入可能藏在内容里**：MDX 和来源文本都当作资料，不当作系统指令。
- **匿名公开接口容易被滥用**：生产限流和预算闸门是上线前置条件，不依赖前端限制。
- **流式结构化输出复杂**：文字和最终推荐元数据分事件传输，服务端验证所有推荐。
- **长期记忆涉及隐私**：首版只在浏览器本地保存少量信息，并提供清除能力。
- **编辑器位于独立仓库**：网站 schema 先合并，编辑器表单随后同步，实施时需要分别记录变更和验收结果。

## 九、与内容编辑器的 Git 隔离

这是实施中的硬性要求：开发 AI 陪伴功能产生的代码、配置和文档改动，不能被内容编辑器算作阻塞发布的未提交更改，也不能在编辑器新增或发布内容时被暂存、提交或推送。

不能只修改编辑器的脏工作区检查，让它“忽略 `src/` 等路径”。这种做法虽然可能解除界面阻塞，但仍存在以下问题：

- 网站构建会读取混有开发改动的工作树，内容验收结果不再可复现。
- 已暂存文件、重命名和跨目录改动可能被误带入内容 commit。
- 如果当前分支已有尚未推送的功能 commit，普通 `git push` 会连同这些祖先 commit 一起推送。

因此采用独立内容发布 worktree：

```text
D:/projects/cp-site/                  AI 功能与网站日常开发工作区
D:/projects/cp-site-content/          内容编辑器专用 Git worktree
D:/projects/cp-site-editor/           独立内容编辑器应用
                                      ↓ CONTENT_REPO_PATH
                                      D:/projects/cp-site-content/
```

隔离规则：

- 内容编辑器只读取和写入 `cp-site-content`，不再操作正在开发 AI 功能的 `cp-site` 工作区。
- 内容 worktree 使用专用内容发布分支；开始编辑前同步远端目标分支，存在分叉时停止并提示处理。
- 编辑器仍执行严格的“工作区必须干净”检查，但检查对象仅为内容 worktree。
- 一次内容操作只允许暂存明确白名单：`content/**` 和本次新增或替换的静态资源。
- 提交前后分别读取 staged file list；出现 `src/**`、配置、文档或任何非白名单路径时立即停止。
- push 前验证待推送 commit 范围；只要范围中包含非内容文件，就拒绝推送。
- AI 功能需要修改 Story schema 时，先通过正常网站开发流程单独合并；内容编辑器随后再开始写入依赖该 schema 的故事。
- 不通过自动 stash、强制 checkout、忽略脏文件或把开发分支直接设为编辑器目标来绕过隔离。

验收场景：

1. 在 `cp-site` 中保留未提交的 AI 功能改动，编辑器仍能在内容 worktree 正常新增草稿。
2. 内容发布生成的 commit 只包含允许的 MDX 和静态资源。
3. 内容分支待推送范围混入任意代码或文档文件时，编辑器拒绝 push。
4. 内容发布后，`cp-site` 中原有未提交改动保持原样，且不会出现在远端内容 commit 中。

## 十、推荐执行顺序

```text
契约与人格
  → Story Schema + 5～10 条样本
  → 检索与意图测试
  → Mock Provider + API
  → 聊天 UI
  → 一个真实 Provider
  → 当前页面上下文与推荐
  → 轻量记忆
  → 编辑器故事库
  → 30～50 条真实故事
  → 50～100 条盲测评测集
  → 限流/预算/隐私
  → 小流量灰度
  → 正式开放
```

第一段可交付里程碑应收敛到“5～10 条故事 + mock provider + 可操作聊天抽屉 + 页面上下文 + 真实卡片跳转”。先验证完整体验，再投入大量内容整理和多模型比较。
