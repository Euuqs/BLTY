# 柏里挑怡 · 私有内容编辑器实施计划

> 版本：v1.0 · 2026-08-27
>
> 目标：在不改造现有前台路由、组件和视觉系统的前提下，制作一个只供自己使用的独立内容编辑器。编辑器运行在本机，直接维护本地网站仓库中的同款、行程和动态内容，再通过 Git 提交并推送 GitHub 触发网站的 Vercel 部署。

## 一、当前项目基线

当前项目已经具备内容驱动网站的主体能力，不需要更换技术架构：

- Next.js 16 + React 19 + TypeScript。
- Velite 在构建阶段读取 `content/` 下的 MDX，并生成 `.velite` 数据。
- 内容目录为 `content/same-styles/`、`content/schedules/`、`content/feeds/`。
- 同款图片目前使用 `public/static/same-styles/`，frontmatter 中保存 `/static/...` 路径。
- 成员字段当前使用 `A`、`B`、`both`，前台组件已经依赖这些值。
- 同款价格当前为字符串，前台通过解析字符串完成价格排序。
- 前台页面直接导入 Velite 集合，内容默认在构建时确定。

因此编辑器应当适配现有内容格式，而不是先迁移全部历史内容。

编辑器写回 MDX 时必须保留未被表单管理的 frontmatter 字段和正文格式，不能因为一次编辑丢失历史标签、扩展字段或换行内容。写回前先创建内存中的完整文件，再只替换明确管理的字段。

## 二、独立编辑器形态

编辑器是一个独立工具，不需要与前台共用同一套页面布局、导航或视觉装饰：

- 编辑器使用自己的根布局、导航、表单组件和错误提示。
- 不要求复用前台的 Bento 卡片、萌宠、渐变和滚动动效。
- 可以采用更朴素的工作台风格，优先保证录入效率、信息密度和防误操作。
- 编辑器只消费和写入网站内容，不负责编辑网站页面布局。

### 推荐运行方式

由于编辑列表明确读取本地仓库，第一版编辑器不部署到 Vercel，而是作为独立的本机 Next.js 应用运行：

```text
cp-site/                  网站仓库
cp-site-editor/           独立编辑器项目
                          ↓ CONTENT_REPO_PATH
                          cp-site/content/
                          cp-site/public/static/
```

编辑器通过环境变量或启动配置获得网站仓库路径，例如 `CONTENT_REPO_PATH=D:/projects/cp-site`。编辑器只绑定 `127.0.0.1`，不直接暴露到公网；这样可以直接读取和写入本地文件，也不需要把 GitHub Token 放进线上服务。编辑器列表和编辑页都以该本地仓库为即时数据源，不读取可能过期的线上 Velite 构建产物。

Windows 本机提供双击启动脚本和桌面快捷方式：入口会检测 `127.0.0.1:3001`，编辑器未运行时在后台启动，等待页面就绪后再打开浏览器。编辑器顶部提供“预览本地网站”按钮，固定检测 `127.0.0.1` 的配置端口；网站未运行时从 `CONTENT_REPO_PATH` 启动开发服务器，确认页面属于当前网站后才在新窗口打开。

如果未来需要从手机或其他电脑使用编辑器，就不能继续读取本地仓库，必须改为部署独立编辑器并通过 GitHub API 或其他远程存储读取内容。这个选择应作为另一种部署模式单独设计。

## 三、首版范围

首版必须覆盖以下三类内容，开发阶段只是交付顺序，不代表行程或动态属于可选功能：

1. 本地编辑器启动、仓库路径配置和连接检查。
2. 同款、行程、动态都具备列表、搜索、编辑、新建和删除。
3. 服务端表单校验。
4. 同款图片上传、预览、替换。
5. 保存草稿和立即发布。
6. 本地 Git 原子提交、推送及清晰的操作反馈。
7. 兼容现有 MDX 文件和历史数据。

标签也属于首版的辅助能力：支持读取同款和动态已有标签、在编辑表单中选择或新增标签，并提供基础标签列表。首版暂不实现定时发布、回收站、批量编辑、多人权限、富文本、图库、部署状态、历史版本恢复和复杂标签改名/合并。

### 首版能力矩阵

| 内容类型 | 新建 | 编辑 | 删除 | 草稿/发布 | 特有能力 |
|---|---:|---:|---:|---:|---|
| 同款 | 必须 | 必须 | 必须 | 必须 | 图片上传、价格、分类、标签 |
| 行程 | 必须 | 必须 | 必须 | 必须 | 具体时间 / 全天 / 待定 |
| 动态 | 必须 | 必须 | 必须 | 必须 | 来源链接、来源平台、标签 |
| 标签 | 基础新增 | 列表 | 暂不删除 | 不适用 | 候选读取、去重 |

## 四、数据兼容原则

### 4.1 成员字段

继续使用现有值：

```text
A      柏欣妤
B      朱怡欣
both   双人
```

后台只显示中文名称。不要在第一版把全部历史内容改成 `bai/zhu`，避免影响首页、搜索、统计和三个内容页。

### 4.2 稳定 ID 与 slug

- 新内容增加稳定 `id` 字段，使用 ULID 或 UUID。
- 旧内容没有 `id` 时，由文件路径生成兼容 ID，首次编辑时再补写。
- 历史内容继续保留现有 `slug` 和前台锚点，标题修改不追溯重命名旧文件。
- 新内容文件名使用 `id.mdx`，同时首次创建时写入固定 `slug`；标题或日期修改不自动改变该 slug。
- 如果旧内容没有固定 slug，继续按现有标题和日期生成，编辑器只保证通过 ID 找到它，不在首版批量迁移旧锚点。

### 4.3 状态字段

增加可选字段：

```yaml
status: published # draft | published
updatedAt: 2026-08-27T12:00:00+08:00
publishedAt: 2026-08-27T12:00:00+08:00
```

所有时间戳统一保存为带 `+08:00` 的 ISO 8601 字符串；内容日期仍是站点使用的本地日期，不转换成 UTC 日期。

历史文件没有 `status` 时，在 Velite transform 中按 `published` 处理。Schema 对 `status` 使用固定枚举 `draft | published`，不接受任意自定义状态。由 `src/lib/velite.ts` 暴露统一的已发布集合，首页、统计、搜索、站点地图和内容页全部使用该出口，避免遗漏草稿过滤。

首版草稿仍需满足当前构建所需的基本结构，暂不支持“只上传图片、其他字段完全为空”的半成品草稿。这样可以避免不完整 MDX 让 Velite 或前台构建失败。

### 4.4 现有字段映射

#### 同款

保留现有字段：`title`、`date`、`category`、`member`、`brand`、`price`、`cover`、`tags`、正文。

- `category` 继续使用：衣服、饰品、零食、美妆、鞋包、其他。
- `price` 首版兼容现有字符串；新内容可在服务端保存为数字字符串，待单独迁移后再改 Schema 类型。
- `cover` 继续写入 `/static/same-styles/<filename>`。
- 图片文件名使用内容 ID，不使用标题，避免改标题时产生图片迁移。

#### 行程

保留现有字段：`title`、`date`、`time`、`member`、`type`、`location`、`description`。MDX 正文首版不作为行程的主要展示字段。

新增 `timeMode`：

```text
具体时间 | 全天 | 待定
```

读取历史数据时：有 `time` 视为具体时间，没有 `time` 默认按待定处理。`type` 继续兼容现有的综艺、直播、演出、活动、其他。

#### 动态

保留现有字段：`title`、`date`、`member`、`type`、`description`、`link`、`tags`，新增可选 `sourcePlatform`。动态正文首版使用 `description`，因为当前时间线实际展示的是该字段；MDX body 保持可选，不要求编辑者填写。

- `type` 继续使用现有的路透、日常、舞台、采访、其他。
- `sourcePlatform` 首版由链接 hostname 自动识别，也允许手动覆盖；不抓取第三方内容。
- 编辑器将“正文”输入保存到 `description`，使用纯文本 textarea；服务端限制长度并清理不可见字符。

## 五、发布模型

### 5.1 草稿与立即发布

编辑页提供：

```text
保存草稿    发布
```

两者都通过同一个服务端写入流程完成：

```text
表单校验 → 生成/更新 MDX → 处理图片 → 创建 GitHub Commit
```

草稿写入 GitHub 并保留版本历史，Velite 和前台按 `status` 过滤。

### 5.2 定时发布推迟到第二阶段

当前前台直接使用构建期 Velite 数据。提前提交 `publishAt` 并不会在指定时间自动触发新构建，因此首版不承诺定时发布。

第二阶段再从以下方案中选定一个：

- Vercel Cron 调用 Deploy Hook；
- GitHub Actions 在发布时间触发构建；
- 将受影响页面改为运行时过滤并配置合适的缓存策略。

在方案确定前，编辑器不显示“定时发布”按钮。

## 六、本地仓库与 Git 写入设计

### 6.1 权限

- 编辑器只允许访问 `CONTENT_REPO_PATH` 指定的目录，并拒绝路径穿越和仓库外写入。
- 编辑器仅绑定本机地址；如果需要局域网访问，必须另外增加密码和 HTTPS 保护。
- 本机 Git 凭据由 Git Credential Manager、SSH 或用户已有的 Git 配置管理，不写入编辑器配置文件。

### 6.2 原子提交

一次操作涉及 MDX 和图片时，在本地工作树中一次完成写入、暂存和 commit，避免出现“图片成功、内容失败”的半完成状态。写入前先检查当前分支和工作区；发现非编辑器产生的未提交修改时默认停止操作并显示文件清单，禁止覆盖或自动 stash 用户修改。

commit message 统一由服务端生成，例如：

```text
content(same): add Adidas jacket
content(schedule): update Hangzhou event
content(feed): delete Weibo update
```

写入接口需要处理 Git 冲突、推送失败、网络中断和重复点击；失败后不能静默重试造成重复 commit。只允许推送当前配置分支，禁止 force push。推送前运行一次 Velite 校验，构建失败则阻止 push。

### 6.3 图片处理

首版限制 JPG、PNG、WebP，限制文件大小和最大尺寸，输出到现有目录：

```text
public/static/same-styles/
```

图片删除默认只删除内容引用，不自动删除文件，避免误删共享资源。图片压缩和 WebP 转换可以在确认 Vercel Node Runtime 的体积、超时和依赖支持后加入。

## 七、编辑器页面

```text
编辑器根地址： http://127.0.0.1:3001/
/
/same-styles
/same-styles/new
/same-styles/[id]
/schedule
/schedule/new
/schedule/[id]
/feed
/feed/new
/feed/[id]
/tags
```

标签管理首版不做改名、合并和删除。编辑器从同款和动态的现有 `tags` 合并生成候选，允许在表单中新增标签，并提供基础标签列表；这样与首页同时统计同款和动态标签的现状保持一致，也不会引入批量重写风险。

编辑器采用独立的工作台布局：桌面端使用侧边栏加内容区，移动端使用折叠导航。可以复用少量基础 CSS token，但不要求延续前台字体、颜色、圆角或装饰动效。优先保证清晰、快速、稳定和防误操作。

## 八、安全要求

- 编辑器默认只绑定 `127.0.0.1`，不提供公网访问入口。
- 本地仓库路径必须经过规范化和边界检查，所有写入都限制在目标仓库内。
- 写入接口校验请求方法、输入长度、内容类型和图片 MIME 类型。
- 本机 Git 凭据不写入编辑器配置文件，也不能出现在界面或日志中。
- 来源链接使用 URL hostname 解析，不能用简单字符串包含判断。
- 发布、删除和替换图片都需要二次确认。

## 九、分阶段实施

### Phase 0 · Schema 与写入基础

- 为 Velite 增加兼容的 `id`、`status`、时间模式和时间戳字段。
- 编写成员、状态、价格和路径的兼容映射。
- 在独立编辑器中实现 frontmatter/正文解析和写回，字段契约以网站现有 Schema 为准，不直接读取 `.velite` 构建产物。
- 编写本地 Git 提交/推送和错误处理模块。
- 完成本地仓库路径校验、Git 操作封装和构建前校验。

验收：历史内容构建结果不变；编辑器能读取、修改并原样保留未知 frontmatter；草稿不会出现在任何前台页面。

### Phase 1 · 同款垂直闭环

- 完成同款列表、搜索、筛选、编辑和新建。
- 完成图片上传、预览、替换和引用写入。
- 完成保存草稿、立即发布、删除确认和操作进度。

验收：新增或修改一条同款后，本地仓库产生一个可读 commit 并成功推送 GitHub；编辑器完成本地 Velite/build 校验，前台图片和价格排序正常。Vercel 部署结果作为后续异步状态，不作为编辑器提交成功的前置条件。

### Phase 2 · 行程、动态与基础标签

- 按现有字段分别实现行程和动态表单。
- 行程加入“具体时间 / 全天 / 待定”交互。
- 动态加入来源平台识别和纯文本清理。
- 增加标签候选、去重、新增和基础列表。

验收：三类内容都可以独立完成新建、编辑、删除、草稿和发布；旧字段仍能正常显示，新字段不会破坏首页、搜索和详情弹窗。

### Phase 3 · 运营增强

- 根据实际使用情况增加定时发布。
- 增加标签改名、合并和未使用标签清理。
- 再评估部署状态、Git 历史查看和内容复制。

## 十、首版验收清单

- [x] 旧 MDX 无需一次性迁移即可构建。
- [x] 成员 `A/B/both`、现有分类和图片路径保持兼容。
- [x] 草稿不出现在首页、内容页、搜索和 sitemap。
- [x] 一次发布最多产生一个内容 commit。
- [x] 图片上传失败、构建失败或 Git 推送失败时，编辑器明确显示失败阶段并按规则回滚。
- [x] 编辑器不能访问目标仓库以外的文件，也不会覆盖用户已有未提交修改。
- [x] `npm run lint`、`npx tsc --noEmit --incremental false`、`npm run test:write` 和隔离 Webpack 生产构建通过。

验收使用完全隔离的网站副本、编辑器副本和本地裸 Git 远端完成，覆盖同款、行程、动态的新建草稿、发布、编辑、删除、图片上传、单次提交、普通推送、失败回滚及前台可见性。为避免污染真实内容，本轮没有向真实 GitHub 推送测试数据，也没有触发真实 Vercel 部署；首次正式使用前仍需复核 Vercel Production Branch 为 `master`。

这份计划的核心约束是：**独立编辑器必须完整覆盖同款、行程和动态三类内容，适配当前的 Velite 内容结构，先完成可靠的草稿/发布闭环，再根据实际使用量增加定时发布和批量运营能力。**
